# Falak

## The problem

Every year in Indonesia, people wait to hear when Ramadan, Syawal and Dzulhijjah begin. Sometimes different organisations announce different dates. They use different calculation criteria (hisab) for whether the new crescent moon, the hilal, can be seen. The government's sidang isbat combines calculation with sighting reports, but the public only hears the verdict.

Existing Hijri date converters are either lookup tables with no astronomy behind them, or official tools that give an answer without showing why. I built Falak for Muslims who want to check the dates and prayer times themselves, for teachers of ilmu falak in madrasah and pesantren, and for developers who want an open implementation.

## What I built

### I compute the sun and moon myself

I implemented standard published models for the sun's and moon's positions directly, with no outside astronomy service. The engine needs no API key and works offline. Every number the app shows traces back to a formula in the repository. Each answer, such as whether the hilal is visible, when Maghrib falls or which way the qibla lies, comes with a panel showing the raw figures behind it: altitude, elongation, moon age and lag time.

### Three methods side by side

I implemented three competing criteria for crescent visibility: Wujudul Hilal, MABIMS-2021 and Odeh. Each runs independently, and a Method Divergence page shows where they agree and where they split. The app doesn't announce dates. It shows what each method computes for a given evening and place. The Indonesia map checks 3,255 points across the country. On some evenings the visibility line cuts through Sumatra and Java, so the same date starts a different Hijri day depending on where you stand.

### I validated the engine before building any screens

My build plan had one rule: no calculation feature ships without validation. Before any interface work, I checked the engine against JPL's DE440 ephemeris, a research-grade reference, for 50 historical new moons. Every one matched within five minutes. The reference library runs only in tests, never in the app. The Isbat Accuracy page compares each method with past Kemenag announcements, entered from cited records only.

### The whole app moved into the browser

The first version had a Django backend. Every endpoint was a pure calculation, the database only cached results, and the engine used nothing beyond standard maths. So it didn't need a server. I ported the engine to TypeScript and published a static site on GitHub Pages. Hosting costs nothing, and a server outage can't break it. The 3,255-point map now spreads across up to eight background threads and renders in about 1.6 seconds, down from 6.3.

### The original engine checks the port

Two copies of a religious-calendar engine will drift unless something stops them. I kept the Python engine as the reference and froze its answers for about 2,083 test cases. The build replays them through the TypeScript port and blocks the deploy on any mismatch. It caught one point off Merauke where moon altitude differed by 0.00000016 degrees. The cause was how the port stored time. Near the 3° MABIMS threshold, that error could have flipped a verdict.

## Result

Falak is live and free, with $0 hosting. All nine pages compute results in the browser with no console errors. It covers Hijri conversion, hilal visibility, the Indonesia map, prayer times with a printable monthly schedule, and the qibla. The qibla page includes Rashdul Qibla: the dates when the sun stands over the Kaaba, so anyone can find the qibla from a shadow. Method Divergence, the Visibility Calendar, Isbat Accuracy and sun calibration were planned for a later phase and shipped anyway. The original feature set took about three days in July 2026. A later pass that month moved it into the browser.

## Under the hood

- Solar positions use a truncated VSOP87 model; lunar positions use ELP2000 as given by Meeus. The Python engine imports only `math` and `datetime`.
- Validation: Skyfield with the JPL DE440 ephemeris, 50 historical conjunctions within a 5-minute tolerance, on a rolling window ending in the current year. Skyfield lives only in `requirements-dev.txt`.
- The shared `CalculationPanel` component shows altitude, elongation, moon age, illumination and lag time for every verdict.
- Five models: `Location`, `ConjunctionEvent`, `PrayerTimeConvention`, `VisibilityResult`, `IsbatRecord`. A cache miss always recomputes from the engine. `IsbatRecord` is seeded from cited sources, never back-computed from the engine, to avoid circularity.
- The grid is 0.5° steps. It began as the Celery task `precompute_visibility_grid`, then moved to Web Workers (one per core, capped at eight) with live progress.
- The 10 endpoints kept their names and response shapes as browser functions, so the nine page components needed almost no edits. The backend stays as the oracle and still runs under Docker Compose. The rejected alternative, Fly.io with web, worker, Postgres and Redis, was priced at about $6–11 a month.
- The Merauke bug: instants were float milliseconds. Bisection on rise and set times drifted a fraction of a microsecond off the grid, `julianDay` divides by 86400 and sidereal time multiplies by 360.98, so it surfaced as a 1.6×10⁻⁷° altitude error while 362 other points matched. Fixed with integer microseconds, as Python's `datetime` uses. The tolerance was then tightened.
- CI runs the Python suite with a Postgres service, regenerates the fixture, compares it numerically at 1e-9 (macOS libm and glibc differ in the last digit of `sin`/`cos`/`atan2`), compares verdicts, dates and booleans exactly, then runs the Vitest conformance suite.
- Map colours were run through a CVD and contrast validator. The old "criterion met" teal measured ΔE 12.8 against slate, below the floor of 15. New steps clear 21.1 (light) and 25.3 (dark), and "met" is a filled square while "not met" is a small dot.
- The coastline is extracted once at build time from Natural Earth via `world-atlas` and `topojson-client` into a committed 111 KB GeoJSON. Prayer times resolve the timezone with `tz-lookup`; an early bug showed them in raw UTC.
- 100 backend tests and 51 frontend tests gate the deploy. The engine is 1,544 lines of Python and 2,313 lines of TypeScript in 15 modules. 86 commits by one author, 5 to 31 July 2026.
