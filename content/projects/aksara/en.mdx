# Aksara

## The problem

Otorita IKN produces a lot of institutional knowledge across its ten Eselon-1 units: regulations, technical reports, academic studies and field notes. The old system kept it all but made it hard to use. There was no search, so staff asked colleagues for files over chat. Uploading meant a long two-step form with no drafts, so most knowledge never got uploaded. Managers had no view of what existed or which units were contributing.

Three groups share Aksara: the public, browsing published knowledge with no login; staff, uploading and reading internal material; and verifiers, curators and administrators, who approve and organise it. Much of the material isn't public, and some is limited to the directorate that owns it.

## What I built

### Every document gets a permanent public code

Each document has a private internal ID from the moment it's a draft. On its first publish it also gets a public code, and that code is its public address. I chose this because a public link has to be permanent and citable, and a link built from the title would break the moment someone fixed a typo. Codes are never reused, and a document that's unpublished and republished gets its old code back.

### One function decides who can see a closed document

There are three access levels: public, internal to OIKN, and restricted, checked on the server for every request against a person's work unit, rank, roles and any temporary access they were granted. One function decides who can open a restricted document without asking, called from every place a document is served, so the rule can't drift between the listing, search and file downloads. I first gave that power to a broader admin role, then narrowed it to one superadmin role once I saw how sensitive it was. A restricted item still shows up, locked, with a button to request access for 7, 30 or 90 days, or permanently.

### Review follows fixed steps with a full history

A document moves from draft to verification, then curation, then published, or it's returned or rejected. Only the system changes that status, never a manual edit. Verifiers and curators each work a split-screen queue with three choices: approve, return with a required note, or reject. Every step lands on a timeline nobody can edit. A revised, already-published document stays live until the revision passes review again.

### Search that forgives typos and keeps the link

I shipped database full-text search with typo tolerance and a "did you mean" suggestion, behind a single interface so a larger search engine can replace it later without touching the pages. Every filter, sort and page number lives in the address bar, so a filtered result can be bookmarked, shared or refreshed.

### One portal per role

My first version had a role switcher. Two days in, I replaced it with a separate portal for each role, because people holding several roles lost track of which one they were using. National legal records (JDIH) started as their own menu, too, until I merged them into the main listing, because people look for "the regulation", not a document type.

## Result

Aksara has been live in production for Otorita IKN since July 2026, its public portal open to any visitor with no login. What I built alone has kept growing since launch. It now spans 16 backend apps and 45 data models: access control, the review workflow, search, and a federated index of national legal records, with 14 registered API endpoint groups and 206 seeded reference rows behind its categories. A gazetteer for browsing by place, an achievements system for contributors, and an auto-classifier for the legal-records feed were all added after the original plan.

## Under the hood

- Public codes look like `AKS-2026-0042-K7mP` and appear in URLs such as `/pengetahuan/AKS-2026-0042-K7mP`. The sequence part is allocated under a row lock so simultaneous publishes can't collide.
- Access levels Publik / Internal OIKN / Terbatas are resolved in the queryset. `knowledge.access.may_read_any_document` is the one predicate reused by the per-object permission check, its SQL-level twin for query filtering, and the backoffice file gate.
- Attachments are served through an access-checked download endpoint, never raw `/media/` paths. A Celery sweep revokes expired access grants and sends a notification.
- Workflow statuses: Draft → Menunggu Verifikasi → Menunggu Kurasi → Terpublikasi, plus Dikembalikan and Ditolak, changed only through transition services. The per-document timeline is "Riwayat Alur", backed by a global audit log.
- Search is Postgres full-text (GIN indexes, ranking, highlighting) behind a `SearchBackend` abstraction so Elasticsearch can drop in later. A `pg_trgm` trigram fallback powers the "did you mean" suggestions.
- JDIH integration stores only light metadata plus a `last_synced_at`, refreshed by a daily sync task, and live-fetches document content server-side with a short cache. It has grown to include an auto-classifier and its own full-text index on top of the metadata sync the original spec called for.
- A place/gazetteer sub-system for geographic browsing, and an achievements module for contributors, were both added after the original 12-milestone build plan.
- The entity-relationship diagram is generated on request straight from the Django models, so it renders both a docs page and a backoffice "Skema Basis Data" page and never goes stale.
- Portals: Kontributor, Verifikator, Kurator and Administrator, with `active_role` held server-side.
- Contribution is a four-step wizard with drafts, up to 10 attachments, and a CSV bulk import of up to 200 rows where invalid rows land as flagged drafts.
- Django + DRF API-only backend and a React SPA. No component, form or state library on the frontend. No ML in V1.
- 16 Django apps, 45 concrete models, 14 registered DRF viewsets, 206 seeded masterdata rows, 1,595 backend test functions, 53,323 Python lines and 30,022 TypeScript lines, 429 commits between 6 July and 25 September 2026.
