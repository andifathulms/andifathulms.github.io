# Aksara

## The problem

Otorita IKN produces a lot of institutional knowledge across its ten Eselon-1 units: regulations, technical reports, academic studies and field notes. The old system kept it all but made it hard to use. There was no search, so staff asked colleagues for files over chat. Uploading meant a long two-step form with no drafts, so most knowledge never got uploaded. Managers had no view of what existed, what was waiting for review, or which units were contributing.

Three groups share Aksara. The public browses published knowledge without logging in. Staff upload and read internal material. Verifiers, curators and administrators approve and organise it. Much of the material isn't public, and some of it is limited to the directorate that owns it.

## What I built

### Every document gets a permanent public code

Each document has a private internal ID from the moment it's a draft. On its first publish it also gets a public code, and that code is its public address. I chose this because a public link has to be permanent and citable. Drafts and rejected items should have no address anyone can guess. A link built from the title would break the moment someone fixed a typo. Codes are never reused, and a document that is unpublished and published again gets its old code back.

### The server decides who sees what

There are three access levels: public, internal to OIKN, and restricted. I check them on the server for every request, against the person's work unit, rank, roles and any temporary access they were granted. The browser never receives a document it then has to hide. Midway through the build I found attachment links could be guessed, so every download now goes through the same check. A restricted item still shows up in listings with a locked file and a button to request access, granted for 7, 30 or 90 days, or permanently.

### Review follows fixed steps with a full history

A document moves from draft to verification, then curation, then published. It can also be returned or rejected. Only the system changes that status, never a manual edit. Verifiers and curators each work in a split-screen queue with three choices: approve, return with a required note, or reject. Every step is written to a timeline on the document that nobody can edit. If a published document is revised, the live version stays public until the revision passes review again.

### Search that forgives typos and keeps the link

I shipped database full-text search with typo tolerance and a "did you mean" suggestion. The search sits behind a single interface, so a larger search engine can replace it later without touching the pages. Every filter, sort and page number lives in the address bar. A filtered result can be bookmarked, shared or refreshed.

### One portal per role, and regulations in the main listing

My first version had a role switcher. Two days in, I replaced it with a separate portal for each role, because people with several roles lost track of which one they were using. National legal records (JDIH) started as their own menu. I merged them into the main listing, because people look for "the regulation", not "a JDIH document".

## Result

I built Aksara alone, and it has been live for OIKN since July 2026. The public portal is open to any visitor, and staff across the ten Eselon-1 units use it, with three server-checked access levels for public, internal, and restricted documents. A native mobile app now shares the same backend. Suggested reading is based on shared topics and units, so anyone can see why an item was suggested.

## Under the hood

- Public codes look like `AKS-2026-0042-K7mP` and appear in URLs such as `/pengetahuan/AKS-2026-0042-K7mP`. The sequence part is allocated under a row lock so simultaneous publishes can't collide.
- Access levels Publik / Internal OIKN / Terbatas are resolved in the queryset. The database enum kept the PRD's original values (Publik / Terbatas / Tertutup); only the UI labels changed, through one presentation-layer map, because "Terbatas" and "Tertutup" are near-synonyms.
- Attachments moved off raw `/media/` paths onto an access-checked download endpoint. A Celery sweep revokes expired access grants and sends a notification.
- Workflow statuses: Draft → Menunggu Verifikasi → Menunggu Kurasi → Terpublikasi, plus Dikembalikan and Ditolak, changed only through transition services. The per-document timeline is "Riwayat Alur", backed by a global audit log.
- Search is Postgres full-text (GIN indexes, ranking, highlighting) behind a `SearchBackend` abstraction so Elasticsearch can drop in later. A `pg_trgm` trigram fallback powers the "did you mean" suggestions from previously successful queries.
- Listing and facet counts were merged into one round-trip (`with_facets=1`). Filter switching uses `keepPreviousData` so the filter rail doesn't reflow.
- Portals: Kontributor, Verifikator, Kurator and Administrator, with `active_role` held server-side. JDIH records are indexed as metadata by a daily Celery sync and fetched live server-side with a one-hour cache and a fallback. The integration is read-only and the API key stays on the server.
- Keycloak SSO and JDIH were built against mockable client interfaces first, then real implementations. A token-exchange endpoint serves the mobile app.
- Contribution is a four-step wizard with drafts, up to 10 attachments, and a CSV bulk import of up to 200 rows where invalid rows land as flagged drafts.
- Django + DRF API-only backend and a React SPA. No component, form or state library on the frontend. No ML in V1.
- 16 Django apps, 45 concrete models, 14 DRF ViewSets, 206 masterdata rows seeded, 36 page components, 53,323 lines of Python and 30,022 lines of TypeScript, 1,595 backend test functions across 65 test files, 429 commits from 6 July to 25 September 2026.
